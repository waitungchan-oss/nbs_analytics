## Proposed approach

1. Create a conservative `.gitignore` before `git init` / first add.
2. Keep business code, tests, docs, scripts, frontend source, and config templates trackable.
3. Ignore runtime data, SQLite DBs, backup/quarantine DBs, logs, caches, build outputs, venv, node_modules, screenshots, binary exports, and legacy backup folders.
4. Initialize Git only after reviewing ignored vs trackable file list.
5. Make an initial baseline commit after running monitoring checks.
6. Use separate branches/worktrees for Codex workers.
7. Require Hermes to inspect `git status`, `git diff --stat`, targeted tests, and baseline checks before accepting worker output.

## Risks / tradeoffs

- `.nbs_runtime/health_history.jsonl` is generated state. If tracked, every monitor run creates dirty diff. Recommended: ignore by default, keep it local runtime evidence.
- Formal SQLite DB cannot be diff-reviewed meaningfully in Git and may contain operational/customer data. Recommended: do not track DB. Use small anonymized fixtures for tests if needed.
- Existing backup folders are large and include binaries; tracking them will make the repo heavy and unsafe.
- If the user wants remote GitHub/GitLab backup, verify secrets/data policy before pushing.

Track:
- `*.py` source files
