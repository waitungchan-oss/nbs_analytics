正式淨 GMV：SQLite 架構方案

目標：雙正式口徑、可追溯／可回滾，並且不增加現有 Dashboard 的 page-load 計算。

建議方案的資料流
方案 A｜同一 SQLite 的獨立 GMV Ledger + 預計算 Snapshot

效能隔離：退款引擎只在確認／切換版本時執行；頁面只讀 active snapshot。既有正式口徑的 cache token 不因 GMV 版本改變而失效。

方案比較

A｜同一 SQLite、獨立 gmv_ 區域（推薦）

以 gmv_ tables/views 建立 ledger、version 與 snapshot；與現有資料可在同一 transaction 內生成一致結果。

優點

  • 原子性最好
  • 備份與回滾一致
  • 讀取路徑最短

代價

  • 需正式 schema migration
  • 需嚴格表名前綴與權限邊界

B｜獨立 gmv_adjustments.db

退款 ledger 與 snapshot 放在第二個 SQLite 檔，再以 attach 或 application layer 合併讀取。

優點

  • 物理隔離清楚
  • 現有 DB schema 變動較少

代價

  • 跨檔一致性與備份較複雜
  • 部署、health check 增加

C｜只存退款明細、頁面即時計算

每次頁面載入都 join 現有營收與退款明細，動態重算正式淨 GMV。

優點

  • 初期 table 較少
  • 計算邏輯直觀

不符合需求

  • 增加 page-load 時間
  • 版本重現與回滾較弱

請點選你認可的方案；建議選 A。選擇只記錄設計偏好，不會修改任何資料。
